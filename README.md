# BOAT AI 予想サイト

LINEで初回に確認カードの「20歳以上・配信希望」をタップし、「買い目」と聞くと当日のサンプル1レースの3タイプを返す任意機能は、[無料LINEの接続・本人宛テスト手順](ops/line-free-sample.md)を参照してください。年齢・配信希望の文字入力は不要です。初期状態は無効です。対象は運営者が日付ごとに `BOAT_LINE_SAMPLE_RACE` で指定します。全員共通の1レースを固定し、締切90秒前以降は配信しません。

年齢確認は自己申告方式で、未確認・20歳未満・停止済みの方には買い目を返しません。「配信停止」で解除できます。

指定レースの展示後予想が保存されたら、20歳以上・配信希望と回答した方だけへ1日1回、自動配信する任意機能も同じ手順に記載しています。別途有効化が必要で、LINEの月200通の無料枠だけを利用します。

展示後の保存済み予想をThreadsへ投稿する任意機能は、[接続・対象日の設定手順](ops/threads-posting.md)を参照してください。初期状態では無効で、投稿用の別途接続が必要です。

公式の展示データが公表されたレースを自動で予想し、確定結果との照合、学習、区分別の運用実績更新まで行います。

## 画面の構成

上部メニューで「レース情報」「運用実績」「AI学習」を切り替えます。選択中の日付・場・レースは切り替えても保持します。URL末尾の `#races` / `#performance` / `#learning` から各画面を直接開けます。

- **レース情報**：日付の前日・翌日ボタン、公式開催情報に基づく24場の一覧、1〜12Rボタン、保存済み予想。開催のない場は選択できません。買い目はガチガチ・ロマン砲・鬼しぼりを切り替え、「買い目・オッズ」の2列でコンパクトに表示します。出目を1-2-3、1-2-4…の数値順に並べ、推定確率・期待倍率・推奨理由は表示しません。表示順だけを変え、保存済み予想や選定・精算の計算は保持します。6艇の特徴データと手動の再確認は必要なときに開きます。
- **運用実績**：日付・場で確認する日次実績と、過去からの累計実績。日次の的中率を押すと、その区分の的中した場・レース・結果出目・払戻金額の一覧を開きます。予想の種類の切り替えは従来どおり両方に共通です。
- **AI学習**：特徴の重み・学習件数・過去1年の検証進捗。手動の一括操作はメンテナンス内にまとめています。対象はレース情報で選択中の日付・場です。

自動運用の件数は各画面の上部に表示し、詳細な状況は開閉できます。画面切り替えや場・レースの選択では予想の再生成・保存を行わず、保存済みデータを読み取ります。予想・学習計算、買い目、日次・累計の集計条件は従来どおりです。

保存済み予想の表示では、選択した日付・場・レースの最新1件だけをDBから取得します。履歴全体を毎回転送しません。運用実績とAI学習の取得・定期更新は、その画面を開いている間だけ行い、レース情報の読み込みを優先します。予想取得の通信エラーと未保存の404を区別し、通信エラー時は「予想を再読み込み」で保存済みデータを再取得できます。再読み込みによる再予想・保存・学習・投稿は行いません。

開催場一覧は、場名の下に公式開催情報の「初日」「2日目」などの日次を表示し、公式の「最終日」は「優勝戦」と表示します。日次を確認できない場合は「開催」、開催がない場は「開催なし」のままにし、開催開始日からの日数を推測して補いません。

1〜12Rのボタンは、公式結果が公表済みのレースをグレー、結果未確定を白で表示します。中止・不成立が公式に公表されたレースもグレーです。選択中のレースは背景色を変えず青い枠で示し、確定済みも選択して保存予想を確認できます。予想の保存・学習が未完了のレースも、色分けは公式結果を基準にします。日付・場ごとに区別して取得し、表示中の場の確定状況を約60秒ごとに確認します。取得に失敗した場合は同じ日・場の前回確認済みの色を保持し、未確認の状態を結果未確定と断定しません。

`GET /api/race_status?date=YYYYMMDD&stadium=04` は、選択した日付・場の `settled_races` と `cancelled_races` を返す読み取り専用のAPIです。1場の公式結果一覧1ページを読み、結果の3連単と払戻を確認したレースだけを確定扱いにします。同じ日・場への同時アクセスは共有し、通常は60秒キャッシュします。公式ページの種類と日付・場を確認できない応答はエラーとし、空の未確定一覧で代用しません。最近取得した同じ対象の確定状況だけを最大5分まで障害時の代用にできます。台帳・学習・自動投稿の更新は行いません。

鬼しぼりは、ガチガチの最大10点から的中確率が高い3点に絞ります。同じ確率なら期待倍率が高いものを優先し、候補外の高配当を追加しません。EV 1.00の足切りは行わず、ガチガチに3点以上あれば3点、候補が1〜2点ならその件数、候補がなければ買い目なしです。新しい予想に `oni_selection_rule: gachi-top3-probability-v1` を保存し、変更前に保存した予想は画面に「旧ルールの保存予想」と表示します。過去の買い目や運用実績を新しい選定方法で作り直しません。 進行中の旧特徴の過去検証は、区分別の集計条件を途中で混ぜないよう旧選定方法を続けます。

ロマン砲は、ガチガチの補完後の最大10点と同じ出目を除外してから、オッズ50倍以上・推定確率0.2%以上の候補を従来の展開・オッズ・確率の優先順で最大10点選びます。候補が足りない場合は条件を緩めて埋めず、残った件数だけ表示します。鬼しぼりとガチガチの重複は、ガチガチから3点に絞る仕様どおりです。新しい予想には `roman_selection_rule: exclude-gachi-v1` を保存します。変更前の保存済み予想は「旧ルールの保存予想」と表示し、買い目や運用実績を変更しません。過去検証も開始時に選定条件を固定し、既存の検証ジョブは従来の重複を許す条件で継続、新しく開始するジョブから重複を除外します。

## 自動運用

- 日本時間7:00〜23:00に、その日の開催場を確認します。稼働中は各確認サイクルの終了後、約60秒おいて再確認します。
- 締切まで45分以内のレースで、6艇の展示タイム・展示STと120通りの3連単オッズがそろったら予想します。「前走成績」のSTは展示STとして使用しません。
- 締切90秒前以降は新しい分析を開始せず、締切30秒前までに保存できなかった予想は運用実績に含めません。結果公表後に予想を作って実績に追加することもありません。
- 予想は日付・場・レースごとに一度だけ保存し、買い目を固定します。公式の3連単結果・払戻金が確認できたら、照合・学習・実績反映を同じPostgreSQLトランザクションで確定します。
- 通信や保存に失敗したら、確定せず次回再確認します。再起動後も保存済み予想を使い、過去7日間の未反映結果を再確認します。中止やデータ不足などで結果を確認できないレースは実績から除外します。
- 複数のワーカーやデプロイが重なっても、PostgreSQLのロックで自動処理と学習の重複を防ぎます。自動処理中のDBエラーをローカルの空台帳・初期モデルで代用しません。

画面の「自動運転」で本日分の保存・反映・結果待ちと最終確認時刻を表示します。開催場とレースを選ぶと保存済みの自動予想を表示します。画面を開いたままの場合は15秒ごとに状況を更新します。

手動の一括操作は画面下部の「メンテナンス」にまとめ、初期表示では閉じています。必要なときに開き、画面上部で選んだ日付・開催場のAI分析や結果の再確認を実行できます。

「運用実績」は上段に日次実績、下段に保存開始からの累計実績を表示します。初期表示の日付は日本時間の本日で、日付を選ぶと過去の1日分も確認でき、「今日」で本日に戻せます。日付変更は累計の期間に影響しません。予想の種類は両方に共通で、初期表示は自動予想、「すべての保存記録」を選ぶと以前の手動予想も含めます。ガチガチ・ロマン砲・鬼しぼりそれぞれ、回収率・的中率・収支・結果確定数と、的中数・結果待ち数を表示します。各買い目100円で、買い目のある結果確定レースだけを率・収支に含め、区分情報のない旧記録は除外します。日次は精算日ではなくレース開催日で集計します。画面が表示中は60秒ごとにも更新し、日付変更前の遅い応答で新しい日付の実績を上書きしません。

日次実績の「確認する開催場」で、全場または24場から1場を選べます。たとえば日付を2026/10/14、開催場を平和島にすると、その日の平和島の3区分実績を確認できます。「今日」は日付だけを本日に戻し、選択した開催場は維持します。開催場は画面上部の予想対象とは別に選び、未開催・保存記録のない日や場では率と収支を「-」、結果確定数を0Rと表示します。日次の開催場を切り替えても、累計は全場・全日付のままです。

日次の各区分の「的中率」は、的中レース一覧を開くボタンです。選択した日付・場・予想の種類を反映し、場コード順・レース番号順に表示します。払戻金額は各区分の3連単1点100円あたりで、同じレースが複数区分で的中しても他区分の払戻を合算しません。一覧の件数・払戻合計はその区分の集計と一致します。的中0件は空の一覧、結果未確定や明細を取得できない状態ではボタンを無効にします。「閉じる」またはEscapeで閉じ、日付・場・予想の種類を変更した際も前の一覧を閉じます。同じ条件の自動更新では開いた一覧も更新します。累計の的中率は従来の数値表示だけです。

`GET /api/performance?date=YYYYMMDD&stadium=04` の `daily` に指定日・開催場の全保存記録・自動予想それぞれのカテゴリ集計と、対象の `stadium`・`venue` を返します。開催場の省略・空文字は全場、1〜24のコード（例: `04`、`4`）はその場だけを対象とし、不正な開催場は台帳を読む前に400で返します。日付を省略すると日本時間の本日で、区切り付きの日付も受け付け、不正な日付は400で返します。日付・開催場の変更前の遅い応答は、新しい選択の表示に反映しません。既存の全期間集計は従来のフィールドを継続します。過去1年の再現検証は「過去1年の検証・学習」内の成績欄に分け、日次・累計の運用実績には混ぜません。

`daily.category_hits` と `daily.automatic_category_hits` に、各区分の的中明細を返します。明細のフィールドは `date`・`stadium`・`venue`・`race`・`actual_combo`・`payout` です。集計と同じ台帳全体を読み、同一日・同一場・同一レースの最新予想だけを採用するため、末尾100件の `records` に含まれない的中も表示できます。明細の閲覧で予想生成・結果取得・保存・学習は実行しません。

## 本番設定

現在のRenderサービス `srv-das6ofm0tbcc73e2id60` では、既存の `DATABASE_URL` または `POSTGRES_URL` が設定されていれば自動運転を開始します。別の環境で有効にする場合は `BOAT_AUTO_RUNNER=1` とPostgreSQL接続先を設定してください。`BOAT_AUTO_ENABLED=0` で自動運転を停止できます。接続文字列はソースに保存しないでください。

既存の `performance_ledger`・`ai_model_state` テーブルを継続使用し、監視状況用の `boat_automation_state` テーブルを追加します。別の有料サービスを作る設定はありません。

`.github/workflows/boat-auto-monitor.yml` を本番リポジトリ `jupoyo1125/boat-ai-prediction` の既定ブランチへ取り込むと、GitHub Actionsが日本時間7:02〜22:57に5分間隔で `/health` と `/api/automation` を確認します。フォークでは実行しません。GitHubのリポジトリ設定でActionsが有効なことを確認してください。

本番の休止対策は、既存のSupabaseで `pg_cron`・`pg_net` を使う `boat-ai-live-healthcheck` を主系統にします。5分ごとに実行し、日本時間7:00〜23:00だけ `/health` と `/api/automation` へGETします。HTTPの待機上限は90秒で、認証情報・個人データは送信しません。追加のRenderサービスや有料プランは作成しません。設定は `ops/setup_live_monitor.sql` に保存してあり、同じジョブ名での再設定はジョブを増やしません。Cronは `cron.job_run_details`、HTTP応答は `net._http_response` で確認できます。深夜のCron実行はHTTPを送らず、Renderを起こしません。

GitHub Actionsは予備の確認として継続します。定期実行には遅延・欠落があり、2026/10/14は5分の設定に対して実際は約27〜53分間隔でした。公開リポジトリでは60日間更新がないと定期実行が停止するため、Actionsの稼働状況も確認してください。Supabaseの休止・障害や公式データ不足があれば取得できない場合があります。新しい設定での取得率は開催日の保存記録で確認します。

本番反映後は `/api/automation` の `enabled: true`、最終確認時刻、Actionsの実行結果を確認してください。予想がまだ保存されていない場合の実績表示「-」は、確定データがないことを示します。

## Supabaseへの移行

移行機能は環境変数で明示的に有効にするまで動作しません。通常のデプロイでは既存のRender DBを使用します。

`BOAT_SUPABASE_URL` にSupabaseのConnect画面で確認した **Session pooler・5432番ポート** の接続文字列を設定します。TLSを有効にし、パスワードの特殊文字をURLエンコードしてください。Transaction pooler・6543番ポートでは自動処理のセッションロックを使用できないため、移行を拒否します。接続文字列やパスワードをGitHubやチャットに貼らず、Renderの環境変数で管理してください。既存の `DATABASE_URL` / `POSTGRES_URL` はそのまま保持します。

切り替えは次の順序で行います。各段階のデプロイが完了し、旧ワーカーの終了を確認してから次へ進んでください。

1. `BOAT_STORAGE_PHASE=prepare` を設定してデプロイします。自動予想・学習と手動の更新を一時停止し、既存の予想・モデル・実績の読み出しを継続します。更新リクエストには503を返します。
2. `BOAT_STORAGE_PHASE=copy` を設定してデプロイします。起動時に元DBの3テーブルを一貫したスナップショットで読み取り、空の移行先へコピーします。記録ID・JSONの全内容・作成/更新時刻を保持し、全件の件数とSHA-256が一致した場合だけ移行先のトランザクションを確定します。100件に制限される公開APIは使用しません。コピー完了後も更新を停止したままにします。
3. `/health` の `storage.phase: copy`、`verified: true`、移行時の台帳件数・学習件数・結果待ち件数を確認します。Supabase側から独立したバックアップを取得し、元DBと照合します。接続先のテーブルはRLSを有効にし、`anon`・`authenticated`・PUBLICの権限を取り消します。
4. `BOAT_STORAGE_PHASE=supabase` を設定してデプロイします。移行完了記録とコピー内容の一致を初回に再確認してからSupabaseだけを使用し、自動運転を再開します。以降の再起動ではコピーし直さず、新たな学習・実績を継続します。DB障害時に空の台帳や初期モデルへ切り替えません。

移行先に既存データがある場合、コピー後に元データが変わった場合、検証に失敗した場合は起動を停止します。コピーが途中で失敗した場合は移行先全体をロールバックします。検証後の同じコピーの再実行はデータを追加せず一致だけを確認します。

Supabaseでの書き込み再開前なら `BOAT_STORAGE_PHASE=render` で元DBへ戻せます。書き込み再開後は元DBが古くなるため、そのまま戻さず最新データをバックアップして再移行してください。元DBを削除する操作は行いません。

Freeプランの容量・通信量・休止条件を確認し、無料枠内で運用してください。`/health` の移行件数は切り替え時の基準値で、運用開始後の最新実績は `/api/performance`・`/api/model`・`/api/automation` で確認します。Supabase側の公開権限検証には `supabase/tests/boat_storage_rls.test.sql` を使用します。

## 予想と学習に使う4項目

現在の特徴の定義は `racer-course-year-v2` です。全国勝率・当地勝率・平均ST・展示ST・場の直近3日間の艇番別勝率は、現在のスコアの重みに含めません。展示STは展示の公表確認に引き続き使います。

| 項目 | 公式データと使い方 |
| --- | --- |
| モーター | 出走表のモーター2連対率。高いほど高評価。 |
| 展示タイム | 対象レースの直前情報の展示タイム。短いほど高評価。 |
| 節間成績 | 出走表の今節成績から、対象レースより前に確定した着順だけを使用。同日でも対象レース以降の結果は除外。1着5点～6着0点、未完走0点の平均を評価。まだ走っていない場合は中立評価。 |
| 選手別・コース別の過去1年成績 | 登録番号ごとに、全国の公式結果ファイルの「実際の進入コース」で集計。対象レースの日の前日までの暦1年（365日または366日）の、出走数・1着率・2着率・3着率。対象レースは展示の進入順で参照し、艇番を進入コースとみなしません。 |

コースの1着率・2着率・3着率は、それぞれ3連単の1着・2着・3着の評価に別々に使います。「2着以内」「3着以内」の累積率ではありません。出走数には進入コースの記録があるF・L・失格も含め、該当する着順だけを分子に数えます。進入がない欠場は含めません。0走は0%と表示せず「成績なし」にします。

各項目をそのレースの6艇内で0～100に相対評価し、同値または欠測は50の中立評価とします。コース成績の3つの着率は着順ごとに相対評価します。重みの基準はモーター15%・展示タイム30%・節間成績5%・選手別コース成績50%です。この割合から、本命と実際の1着艇の特徴を比較して自動学習を続け、画面には現在の割合を表示します。コースの重みは各着順の評価で共有します。基準変更前の保存モデルは初回の読み込みで新しい割合に移し、変更前の重みを `weight_baseline_history` に残します。同じ基準の学習済み重みは読み込みや再起動で初期化しません。学習件数・的中数・温度・保存済み予想・運用実績を引き継ぎ、保存済みの買い目は再計算しません。画面には生の着率、出走数、集計期間、節間の確定着順を表示します。展示前の評価順では進入未確定のコース成績を中立と表示します。

選手別のコース成績は `boat_racer_course_days` に公式日別集計を保存し、レースのたびに1年分を取得し直しません。サーバー内では同じ対象日の年間集計を共有します。日付が変わったら追加の1日分を取得し、新しい1年窓を作ります。初回準備・中断後の補完は既存サーバーの低優先度処理で行い、ライブ予想と公式通信の上限3を共有します。`BOAT_COURSE_RUNNER=0` でキャッシュ準備だけ停止できます。

1年分がそろわない場合は503・`course_history_pending` と準備済み日数を返し、途中のデータを1年成績と表示しません。過去の日付を分析する場合も、その日より前の1年分が必要です。現在の選手プロフィールの成績を過去の日付へ流用しません。サーバー用キャッシュにはRLSを有効化し、匿名・一般ユーザーのDBアクセスを許可しません。必要に応じて `ops/setup_racer_course_history.sql` で同じテーブルを用意できます。

旧モデルの重み・温度・カウンターは `legacy_model` に保管し、通算の照合数も保持します。新方式の学習件数・的中数は `feature_samples` / `feature_hits` に分けて0から数えます。旧特徴で保存済みの予想は精算・実績反映を続けますが、新しい重みを学習させません。保存済みの買い目や運用実績は再計算しません。既に進行中の過去検証は旧特徴のまま再開し、画面に旧条件と表示します。旧特徴の過去モデルを新方式へ適用する操作は拒否します。新規の過去検証は現在の4項目を使い、対象日前1年のコース成績の準備を待ってから学習します。

## 過去レースの一括処理

AI分析は3レースずつ、結果取得・学習は6レースずつサーバーで処理します。出走表・展示・オッズと履歴の取得には接続を再利用し、公式サイトへの同時アクセスは手動・自動処理を合わせて1ワーカーあたり3件までに制限します。レースごとの固定1秒待機は不要になりました。

公式サイトへの通信は同じ優先度の中で待機順に実行し、接続枠を待つ時間も最大15秒（短い通信タイムアウトの場合はその秒数）に制限します。過去結果ファイルの取得も同じ制限を使います。開催場は日付ごとに15分間、自動運用と画面で共有し、同じ日付の同時取得をまとめます。更新に失敗した場合だけ、1時間以内に確認できた同じ日付の開催場を表示します。別の日付の開催場は流用しません。

画面は開催場の取得に失敗すると2回まで自動再試行します。復旧しない場合は「開催場を再取得」で再確認できます。日付を変更すると前の取得を取り消し、遅れて届いた応答で新しい日付の選択内容を上書きしません。

現在の予想は上記の選手別コース1年成績キャッシュを共有します。旧特徴で開始済みの過去検証に限り、従来の前3日分の全国日別結果と場別集計を使います。検証途中で特徴の定義を切り替えず、保存済みのモデル・進捗と整合させます。

通信枠は3件を維持し、開催中の予想・画面確認を過去検証より先に通します。同じ優先度では待機順を守ります。過去検証が通信枠を待ちきれなかった場合は、再試行失敗を増やさず、保存位置と有効状態を保って60秒後に再開します。実際の通信障害の再試行方針は継続します。

単独のAI予想は、共有スレッドの待機を含め、出走表・展示・オッズの取得を分析開始から45秒までに制限します。コース成績の保存先の読み取りにも接続・SQLの時間制限を設けています。未開始の取得は取り消し、期限切れの取得を後から開始しません。旧特徴の履歴取得の上限は30秒です。公式通信の同時実行数は3件です。

画面の分析通信は応答本文を含め60秒、保存は20秒で打ち切り、「分析中」のまま待ち続けずボタンを戻します。保存の応答が時間切れになった場合は保存完了を断定せず、保存状況の確認を案内します。分析中に日付・場・レースを変えると画面側の通信を取り消し、前のレースの応答で新しい選択を上書きしません。保存済み予想の確認も15秒で時間切れになり、同じレースへの同時取得をまとめます。

分析ではモデルと履歴を共有し、変更したレースの保存を1回のSQLにまとめます。結果は開催場の一覧を共有し、取得できないレースだけ個別ページを確認します。学習は従来と同じレース順・正規化で行い、モデルと台帳を同じPostgreSQLトランザクションで保存します。保存失敗時は両方をロールバックし、再実行や自動処理との重複で二重学習しません。学習済み・結果待ち・予想なし・通信失敗は個別に表示します。

APIは `POST /api/analyze_batch`（最大3件）、`POST /api/settle_batch`（最大6件）で、JSONの `date`・`stadium`・`races` を指定します。画面の一括ボタンはこれらを使用します。既存の単独レースAPIも継続使用できます。

## 過去1年の検証・学習

`POST /api/historical` に `{"action":"start"}` を渡すと、日本時間の前日までの1年間を対象に、専用モデルを初期値から学習します。対象は暦上の1年間で、うるう日を含む区間は366日になることがあります。既存のジョブがある場合は、その保存位置から再開します。画面の「過去1年の検証・学習」から開始・一時停止・再開できます。

- 公式の全国日別結果LZHを取得します。新規モデルは各対象日前の1年分の選手別コース着率と、そのレースより前の節間成績を使います。旧モデルの再開時のみ前3日分の場別結果を再利用します。予測用の出走表・展示は対象レースの公式ページから取得し、結果ファイルの実際のレースSTは予測に渡しません。
- 同じ日の予測では前日までのモデルを固定し、その日の結果を次の日の学習に使います。現在の本番モデルを昔のレースの検証に流用しません。
- 120通りのオッズがそろったレースだけ、現行の3区分の買い目を再現し、各100円・公式3連単払戻金で集計します。過去のページに残る締切時オッズによる再現検証で、締切前に保存した実運用成績とは別です。
- オッズ不足は学習できる場合でも回収率から除外します。出走・展示不足、返還・同着・不完全な結果も別に数えます。通信失敗は欠落扱いにせず、同じ位置で再試行し、5回連続失敗した場合は停止します。
- 3レースずつ進捗・モデル・区分別集計を一括保存します。複数プロセスの排他制御と世代チェックで二重学習を防ぎ、ネットワーク処理中はDBトランザクションを保持しません。日別集計には学習前後のモデルと結果データのハッシュも保存します。
- 自動予想が動く07:00〜23:00は過去取得を1並列、それ以外は最大3並列に制限します。全処理で公式サイトへの同時接続上限3を共有します。生データを全件既存台帳に追加せず、日別集計とチェックポイントを保存します。

`GET /api/historical` と `/api/performance` の `historical` で、進捗と過去検証の成績を確認できます。本番台帳・自動予想の成績には過去検証を混ぜません。

学習済みモデルは自動で本番に適用しません。特徴の定義が本番と同じで、全期間の処理が完了し学習対象が1,000R以上ある場合、画面の適用ボタン、または `{"action":"apply_model"}` で適用できます。適用前のモデルはジョブ内に保存し、既存の学習件数・的中数を維持します。重複し得る過去サンプルは本番のカウンターに加算せず、`historical_training` に分けて記録します。

Renderの休止・再起動中は処理が止まりますが、起動時に再開します。既存の開催時間内の監視ワークフローや画面の進捗取得でサービスを起動できます。1年分にも大量の取得処理があるため、全件完了の時刻は保証しません。`BOAT_HISTORY_RUNNER=0` で過去検証のワーカーだけを停止できます。

予測や実績は将来の的中・利益を保証しません。





## 自動運用のメモリ対策と確認記録

自動運用の巡回では直近7日と当日の自動予想の識別情報だけを読み、保存・精算時は対象レースだけを共通トランザクション内で更新します。他レースの削除や履歴全体の置換を行いません。投稿候補も対象日・対象場だけを読みます。選手別コース成績は7日ずつ読み、1年全体を同時に展開しません。集計期間と着率の計算は同じです。

監視の状態変化をログに記録し、各場の確認後に `boat_automation_state.state.race_events` へまとめて保存します。状態の更新中も同じ日の記録を保持し、日付が変わると切り替えます。`prediction_missing` は公式結果の確定までに予想を保存できなかったレースで、事後予想を作らず実績に加えません。既存の記録だけでは不明な過去の未保存理由を推測して補いません。
