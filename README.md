# BOAT AI 予想サイト

公式の展示データが公表されたレースを自動で予想し、確定結果との照合、学習、区分別の運用実績更新まで行います。

## 自動運用

- 日本時間7:00〜23:00に、その日の開催場を確認します。稼働中は各確認サイクルの終了後、約60秒おいて再確認します。
- 締切まで45分以内のレースで、6艇の展示タイム・展示STと120通りの3連単オッズがそろったら予想します。「前走成績」のSTは展示STとして使用しません。
- 締切90秒前以降は新しい分析を開始せず、締切30秒前までに保存できなかった予想は運用実績に含めません。結果公表後に予想を作って実績に追加することもありません。
- 予想は日付・場・レースごとに一度だけ保存し、買い目を固定します。公式の3連単結果・払戻金が確認できたら、照合・学習・実績反映を同じPostgreSQLトランザクションで確定します。
- 通信や保存に失敗したら、確定せず次回再確認します。再起動後も保存済み予想を使い、過去7日間の未反映結果を再確認します。中止やデータ不足などで結果を確認できないレースは実績から除外します。
- 複数のワーカーやデプロイが重なっても、PostgreSQLのロックで自動処理と学習の重複を防ぎます。自動処理中のDBエラーをローカルの空台帳・初期モデルで代用しません。

画面の「自動運転」で本日分の保存・反映・結果待ちと最終確認時刻を表示します。開催場とレースを選ぶと保存済みの自動予想を表示します。画面を開いたままの場合は15秒ごとに状況を更新します。

「運用実績」は初期表示で自動予想の累計を集計します。「すべての保存記録」を選ぶと以前の手動予想も確認できます。ガチガチ・ロマン砲・鬼しぼりそれぞれ、各買い目100円として、買い目のある結果確定レースだけを集計します。区分情報のない旧記録は区分別実績に含みません。

## 本番設定

現在のRenderサービス `srv-das6ofm0tbcc73e2id60` では、既存の `DATABASE_URL` または `POSTGRES_URL` が設定されていれば自動運転を開始します。別の環境で有効にする場合は `BOAT_AUTO_RUNNER=1` とPostgreSQL接続先を設定してください。`BOAT_AUTO_ENABLED=0` で自動運転を停止できます。接続文字列はソースに保存しないでください。

既存の `performance_ledger`・`ai_model_state` テーブルを継続使用し、監視状況用の `boat_automation_state` テーブルを追加します。別の有料サービスを作る設定はありません。

`.github/workflows/boat-auto-monitor.yml` を本番リポジトリ `jupoyo1125/boat-ai-prediction` の既定ブランチへ取り込むと、GitHub Actionsが日本時間7:02〜22:57に5分間隔で `/health` と `/api/automation` を確認します。フォークでは実行しません。GitHubのリポジトリ設定でActionsが有効なことを確認してください。

無料Renderのスリープ対策に定期アクセスを使用しますが、GitHub Actionsの定期実行は遅延・欠落する場合があり、全レースの取得は保証されません。公開リポジトリでは60日間更新がないと定期実行が停止するため、Actionsの稼働状況も確認してください。無料PostgreSQLには有効期限があるため、継続運用には保存先の期限管理が必要です。

本番反映後は `/api/automation` の `enabled: true`、最終確認時刻、Actionsの実行結果を確認してください。予想がまだ保存されていない場合の実績表示「-」は、確定データがないことを示します。

## Supabaseへの移行

移行機能は環境変数で明示的に有効にするまで動作しません。通常のデプロイでは既存のRender DBを使用します。

`BOAT_SUPABASE_URL` にSupabaseのConnect画面で確認した **Session pooler・5432番ポート** の接続文字列を設定します。TLSを有効にし、パスワードの特殊文字をURLエンコードしてください。Transaction pooler・6543番ポートでは自動処理のセッションロックを使用できないため、移行を拒否します。接続文字列やパスワードをGitHubやチャットに貼らず、Renderの環境変数で管理してください。既存の `DATABASE_URL` / `POSTGRES_URL` はそのまま保持します。

切り替えは次の順序で行います。各段階のデプロイが完了し、旧ワーカーの終了を確認してから次へ進んでください。

1. `BOAT_STORAGE_PHASE=prepare` を設定してデプロイします。自動予想・学習と手動の更新を一時停止し、既存の予想・モデル・実績の読み出しを継続します。更新リクエストには503を返します。
2. `BOAT_STORAGE_PHASE=copy` を設定してデプロイします。起動時に元DBの3テーブルを一貫したスナップショットで読み取り、空の移行先へコピーします。記録ID・JSONの全内容・作成/更新時刻を保持し、全件の件数とSHA-256が一致した場合だけ移行先のトランザクションを確定します。100件に制限される公開APIは使用しません。コピー完了後も更新を停止したままにします。
3. `/health` の `storage.phase: copy`、`verified: true`、移行時の台帳件数・学習件数・結果待ち件数を確認します。Supabase側から独立したバックアップを取得し、元DBと照合します。接続先のテーブルはRLSを有効にし、`anon`・`authenticated`・PUBLICの権限を取り消します。
4. `BOAT_STORAGE_PHASE=supabase` を設定してデプロイします。移行完了記録とコピー内容の一致を初回に再確認してからSupabaseだけを使用し、自動運転を再開します。以降の再起動ではコピーし直さず、新たな学習・実績を継続します。DB障害時に空の台帳や初期モデルへ切り替えません。

移行先に既存データがある場合、コピー後に元データが変わった場合、検証に失敗した場合は起動を停止します。コピーが途中で失敗した場合は移行先全体をロールバックします。検証後の同じコピーの再実行はデータを追加せず一致だけを確認します。

Supabaseでの書き込み再開前なら `BOAT_STORAGE_PHASE=render` で元DBへ戻せます。書き込み再開後は元DBが古くなるため、そのまま戻さず最新データをバックアップして再移行してください。元DBを削除する操作は行いません。

Freeプランの容量・通信量・休止条件を確認し、無料枠内で運用してください。`/health` の移行件数は切り替え時の基準値で、運用開始後の最新実績は `/api/performance`・`/api/model`・`/api/automation` で確認します。Supabase側の公開権限検証には `supabase/tests/boat_storage_rls.test.sql` を使用します。

## ローカル起動と検証

```bash
pip install -r requirements.txt
python app.py
```

ブラウザで `http://127.0.0.1:8000` を開きます。PostgreSQL未設定のローカル環境では手動操作とJSON保存を使用し、自動運転は開始しません。

```bash
python -m unittest discover -s tests -p 'test_*.py' -v
node tests/test_batch.cjs
node tests/test_automatic_ui.cjs
```

検証には一時保存先と模擬データを使用し、本番の学習・実績を変更しません。自動予想から精算まで、締切保護、再起動時の再確認、重複防止、DB障害時の停止、画面の実績切替を確認します。

予測や実績は将来の的中・利益を保証しません。
